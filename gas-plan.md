# Gasless trading implementation plan

## Scope and investigation baseline

Phase 0 evidence remains partial. Following the user’s explicit instruction to implement from `api.yaml`, Phase 1 API/policy code is implemented; validation limits are recorded below. Requirements: `gas.md`. Repository guide: `AGENTS.md` (the file is uppercase). Investigated on 2026-10-22 against the working tree, including the existing Credits UI. The September deployment snapshot in `gas.md` is historical, not a verified current environment state. No live transaction, backend deployment, or wallet signing was tested.

Implement Credits/gasless and explicitly selected MVRK payment for **secondary orderbook buy, sell, cancellation and refund**, plus prepaid-credit top-ups. Primary launchpad purchases and Ethereum bridge actions are not relay intents in this specification; preserve their existing execution. Do not claim that Profile Credits makes unsupported primary/bridge actions gasless.

The implementation should reuse the current forms, validation, wallet, authenticated RWA client, React Query cache and notifier socket. New modules below have proposed names; existing paths are identified separately. Do not introduce a second wallet client, socket, generic transaction framework, or replacement Credits UI.

## 1. Current implementation and gaps

### Execution and validation

- `app/routes/trade.$address/components/BuySellPanel/BuySellPanel.tsx` selects `PrimaryPurchasePanel` or `SecondaryBuySellPanel`. The secondary panel reads `useOrderbookConfig`, passes the verified config into `BuySellContent`, and invalidates open orders/history on success. Its form key identifies the asset/book/token pair; adding payment mode to this key would unnecessarily erase inputs.
- `app/lib/organisms/PriceSection/popups/index.tsx` owns `BuySellContent`, market/limit inputs, quantity/price conversions, liquidity, balance and minimum checks, estimation, confirmation and four `useContractAction` instances. Market and limit actions use the same orderbook buy/sell contracts. Success resets amount, limit price, expiry and gas state.
- `app/contracts/orderbook.contract.ts` owns `buildOrderPayload`, `validateOrderRules`, `orderbookBuyBatch`, `orderbookSellBatch`, direct buy/sell, cancel/refund and buy/sell estimation. Buy/sell construct a wallet batch: add FA2 operator → place order → remove operator. Cancel/refund directly call `.send()`, wait for confirmation, and report confirmation level. There is no permit construction or relay transport.
- Existing validation uses `BigNumber`, `toNatString`, `toPositiveNatString`, `decimalScale`, and `alignQuantityAtomsToTick`. Preserve the separation of price and quantity ticks, explicit token IDs/decimals, currency key, KYC and balance requirements. Extract/export shared payload validation rather than reproducing it for permits.
- `app/hooks/useOpenOrderAction.ts` is the shared cancel/refund adapter; it picks refund when `!order.can_cancel`, invokes direct actions and invalidates open orders/activity. `fetchWalletOpenOrders` in `app/lib/apis/rwa/orders/orders.ts` requests `refund=none,claimable`. Retain claimable-refund eligibility; do not treat every non-cancellable row as claimable if future callers pass a broader set.
- `app/contracts/hooks/useContractAction.tsx` treats a successfully resolved action promise as success, drives direct-wallet callbacks/toasts and forces data refresh. Returning a relay `202` through this hook would incorrectly report order completion. Keep it for direct actions; relay plans need explicit accepted/progress/confirmed states.

### Fees, balances and authentication

- `BuySellContent` debounces direct batch estimates for 400 ms. Failed/unavailable estimates are currently stored as `ZERO`; this cannot support the requirement that unknown fee/balance blocks MVRK execution.
- `app/errors/helpers/estimateAction.helper.ts` exposes `getEstimationBatchResult` and `sendContractBatchOperation`; `walletError.helper.ts::estimateBatchOperation` aggregates `totalCost`, `totalSuggestedFeeMutez` and related fields from Taquito. Internal `Mutez` names already wrap Mavryk `suggestedFeeMumav` values. Verify cost units and storage/reveal inclusion before using the aggregate for affordability.
- `FeesCard.tsx` and `FeesCard.utils.ts` currently combine network gas and orderbook fees into the Platform Fee presentation. These components are also used by primary purchase UI; extend with optional payment-review data without changing primary fee calculations.
- `UserProvider` supplies `userTokensBalances`, populated by TzKT REST/socket helpers in `app/providers/UserProvider/helpers/userBalances.helpers.ts` and `sockets.tsx`. Missing values are often converted to zero by callers/helpers. Credits and native affordability must retain explicit loading/error/known-zero states. Use exact token-address/token-ID identity rather than an ambiguous address-only alias.
- `WalletProvider` supplies `dapp`; `WalletCore.client.ts` supplies the existing Beacon wallet and toolkit. `AuthProvider` exposes `login`, `isAuthenticated`, `isAuthLoading`, `authenticatedWalletAddress`. Connected wallet and authenticated wallet must match.
- `AuthProvider/helpers/utils.ts::signAuthChallenge` demonstrates `getActiveAccount()` and `requestSignPayload`. Its auth payload encoding is specific to login and **must not** be reused as a permit payload format.

### Existing Profile and Credits UI

- `app/routes/portfolio.profile/profile.types.ts` already defines `GasPaymentMethod = "credits" | "mvrk"` and dropdown options. `hooks/useProfileForm.ts` initializes Credits but holds both draft and saved values only in component state; `save` has an API TODO. `route.tsx` already renders Gas Payment → Payment Method → Save. There is no persisted active preference here.
- `app/layouts/PageLayout/ConnectWallet.tsx` always renders `CreditsWalletDropdown`; `MvrkWalletDropdown` is commented out.
- `WalletDropdown/CreditsWalletDropdown/useCredits.ts` starts at 20 credits, supplies a mock USDT balance of 172507.78 and uses a three-second timer to add credits locally. Each hook instance owns isolated state. Replace this with shared authoritative data.
- `credits.utils.ts` hardcodes `CREDIT_PRICE_USD = 1`, healthy/low/empty/pending/free states, 5/20/50 presets and 5–100 custom bounds. It prioritizes pending then free. Price and mixed free/paid precedence are not agreed API contracts.
- `CreditsBalanceBadge.tsx` and `CreditsWalletDropdown.tsx` already render the badge, balance dropdown and modal trigger. Keep this presentation and add unknown/error/no-fee states and real data.
- `WalletDropdown/AddCreditsModal/AddCreditsModal.tsx` already renders presets, custom input, exact-payment copy, non-withdrawable disclosure and submitted/minimize/details UI. It uses floating-point `Number`, assumes $1 per Credit, has no explicit submit-error UI, and routes details to generic activity. It currently promises platform/network fee coverage and one Credit per order without confirmed tariff support. Reuse it, removing these assumptions.

### API, tracking, notifications and history

- `app/lib/apis/rwa/client.ts` is the Axios client with JWT injection and a single auth-refresh retry. `config.ts` takes the base URL from `RWA_API`; other adapters use paths such as `/wallets/...`. Add `/relay/...` relative to this configured API base, not a second hardcoded origin/version prefix.
- Existing RWA adapters use Zod schemas and typed responses. No relay API adapter, permit helper, or gasless execution was found in application code.
- `NotificationsProvider` owns one authenticated socket, wallet subscriptions and event dispatch. Its context exposes `status` and `wallet`; `useNotifierEvent`/`useNotifierChannel` are the integration points. `NotifierWalletEvent` lacks `RELAY_OPERATION_UPDATED`. Notification rows already allow nullable `event_id` and arbitrary kind/payload.
- `NotificationsDataNotifierListener` refetches inbox rows on wallet events. Message templates/helpers need relay-failure wording and coordination with relay terminal toasts. Never synthesize an inbox success row.
- `TransactionsProvider`/`TransactionWidgetProvider`/`RTransactionWidgetHost` implement **bridge-specific** durable tracking and signer-based progress. They are mounted in `app/root.tsx` above the loading gate. Use this placement/lifecycle pattern for relay tracking, but do not feed relay statuses into bridge signers or change bridge settlement rules.
- `portfolio.activity/components/TransactionHistoryTab/TransactionHistoryTab.tsx` uses `fetchWalletOrderHistory`, numbered pagination, search and server sort. That adapter explicitly requests only limit/market buy/sell transaction types. It does not expose top-ups. Relay history instead uses newest-first cursor pagination and `intentKind: fee_top_up` rows.

## 5. Cross-cutting risks and safeguards

1. **Signing compatibility is a hard gate.** Intent fields do not fully specify the contract's signed envelope, counter storage, action type or wallet hash behavior. Use confirmed live-script fixtures; a superficially valid signature is insufficient.
2. **Accepted-but-unacknowledged mutations can duplicate user intent.** Ordinary idempotency and top-up correlation are different capabilities. Unknown work stays locked; a timeout/open-list miss is not permission to sign a replacement or pay MVRK.
3. **Persistent operator permission is deliberate.** Gasless omits revoke; disclose it in review. A later direct batch can revoke that grant, so do not permanently cache “operator already granted”.
4. **Indexers/credits lag chain confirmation.** Order confirmation does not prove fill; top-up confirmation does not justify an optimistic balance. Keep updating states and explicit refresh paths.
5. **Existing global context readiness is coarse.** Avoid making relay/fee loading a global app gate or using zero fallback balances to approve/block the wrong path. Disabled relay must leave MVRK selectable.
6. **Account/network races and cross-tab work matter.** Revalidate scope after every await, scope persistence/caches, and use backend 409 as authoritative concurrency control. Preference storage cannot cancel signed work.
7. **Fee amendments outlive active polling.** Keep mergeable terminal details and credit refresh on amendments; no hardcoded refund policy or local free-credit reset.
8. **Shared UI has primary consumers.** Optional payment props must preserve launchpad summaries and direct APIs. Never apply orderbook permits to primary sales.
9. **Shared HTTP retry can obscure outcomes.** Capture exact request identity before any Axios/auth retry; disable overlapping mutation retry policies and never log signed payloads or secrets.
10. **UI registry differs in detail from guide.** Skill points component discovery to `REGISTRY.md`; AGENTS also requires updating `SKILL.md` for new R components. Maintain both where needed rather than silently ignoring either requirement.
